# 4번 Agent: 현장 도입·사업성 개발 계획 및 작업 기록

작성일: 2026-09-30

## 1. 목적과 범위

Physical AI·Robotics 기업의 제품이 실제 고객 현장에서 사용되는지, 고객에게 어떤 경제적 효과를 제공하는지, 도입을 제한하는 위험이 무엇인지 근거로 분석한다.

- 담당 파일: `src/ai_investment/agents/business.py`
- 입력: `selected_startup`, `profile`
- 출력: `business_analysis`, 실제 분석에 사용한 `references`
- 외부 Tool: Tavily 기반 `web_search`
- LLM: `ChatOpenAI`, 모델명은 `OPENAI_MODEL`에서 읽는다.
- 실행 위치: 분야·고객 분류 이후 기술·시장 Agent와 병렬 실행
- 결과 소비자: 투자 판단 Agent, 보고서 생성 Agent

기술 성능 검증과 시장 규모 분석은 해당 Agent가 담당한다. 이 Agent는 고객 도입, 비용·효과, 상용화 근거, 현장 규제 위험을 담당하며 최종 투자 점수나 `decision`을 작성하지 않는다.

## 2. 현재 상태

| 항목 | 상태 | 확인 내용 |
|---|---|---|
| Agent 기본 파일 | 완료 | `run(state)` 인터페이스와 `TOOLS`가 있으며 분석 로직은 `NotImplementedError` 상태 |
| State 쓰기 계약 | 완료 | `business_analysis`, `references`만 반환하도록 계약 정의 |
| 검색 Tool 기반 | 완료 | 공통 `Evidence` 반환, 호출당 최대 5개 검색 결과 |
| 환경변수 예시 | 완료 | 기준 환경의 변수명 반영, 비밀값은 빈칸 처리 |
| 실행 환경 및 초기화 확인 | 완료 | Python 3.11.15, 프로젝트 `.env` 필수값, ChatOpenAI·TavilySearch 초기화 확인. 실제 API 호출은 미검증 |
| 2단계 입력 계약 및 예시 | 완료 | `selected_startup` 4개 필드와 `profile` 5개 필드, 누락 처리 규칙, 가상 입력 JSON 2개 확정. 실행 로직 반영은 예정 |
| 출력 모델·프롬프트·분석 로직 | 예정 | 아래 순서로 구현 |

문서의 출력 필드와 검색 횟수는 제안이며 구현 단계에서 확정한다. 실제로 검증하지 않은 항목을 완료로 표시하지 않는다.

## 3. 단계별 작업 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | Python 3.11 환경 구성, 의존성 설치, 프로젝트 `.env` 로딩 확인 | 필수 환경변수 존재 여부를 비밀값 출력 없이 확인 |
| 2 | 기업 입력 예시와 분야·고객 분류 입력 형태 확인 | 기업명, 제품, 고객 정보의 실제 전달 형식을 확인 |
| 3 | Pydantic 출력 모델 정의 | 상용화 단계, 고객 사례, 비용·효과, 위험, 출처 ID와 정보 부족 표현 가능 |
| 4 | 검색 질의와 호출 한도 정의 | 고객 도입, 비용·효과, 안전·규제 근거를 검색할 질의 마련 |
| 5 | 분석 프롬프트와 structured output 연결 | 검색 근거만 사용하고 확인 불가와 모순을 명시하도록 구성 |
| 6 | `business.py` 분석 흐름 구현 | 입력 검증부터 분석·인용 검증·State 변경분 반환까지 동작 |
| 7 | 검색·LLM 대체 응답으로 테스트 | 시연, 유료 운영, 정보 부족, 모순, 실패 사례 처리 확인 |
| 8 | 실제 기업 1개로 실행 | 주장·수치·출처를 원문과 대조하고 결과 기록 |
| 9 | Graph 통합 검증 | 병렬 Agent와 충돌 없이 투자 판단에 결과 전달 |

### 1단계: 환경 구성

필수 변수는 `OPENAI_API_KEY`, `OPENAI_MODEL`, `TAVILY_API_KEY`다. LangSmith 관련 변수는 선택 사항이다. `.env.example`은 공유용 변수 목록이며 실제 실행값은 프로젝트 `.env`에 보관한다.

```bash
uv venv --python 3.11
uv pip install --python .venv/bin/python -r requirements.txt
```

환경 로더는 저장소의 기존 구현이 있는지 먼저 확인한다. 없다면 프로젝트 `.env`를 명시적으로 로딩한다. 기존 `.env`를 덮어쓰지 않으며 키와 토큰은 로그·문서·테스트 데이터에 기록하지 않는다.

### 2~3단계: 입력과 출력 계약

입력 계약은 [Basecode 개발 계약](BASECODE.md#4번-agent-입력-계약)에 기록했다. `selected_startup`은 `name`, `product`, `funding_stage`, `team`을 사용한다. `profile`은 `subdomain`, `paying_customer`, `customer_problem`, `info_sufficiency`, `missing_info`를 사용한다.

기업명이 없거나 공백뿐이면 `ValueError`로 처리한다. 제품·고객 정보가 부족하면 누락 필드를 기록하고 기업명으로 검색한다. `profile`이 없어도 기업명이 있으면 진행하며, 값이 제공되었는데 타입이 잘못된 경우에는 `TypeError`로 처리한다. 상위 Agent의 `missing_info`도 보존한다. 병렬 실행되는 `technical_analysis`, `market_analysis`를 입력 전제로 사용하지 않는다.

테스트용 입력은 다음 두 가지이며 모두 가상 기업이다.

- [정보가 갖춰진 입력](../tests/fixtures/business_input_complete.json): 기업 4개 필드와 사용자 제공 `profile` 5개 필드를 포함한다. `충분`은 입력 충분성 표시이며 유료 운영 근거가 있다는 의미가 아니다.
- [기업명만 있는 입력](../tests/fixtures/business_input_name_only.json): `profile`과 선택 기업 정보 없이도 기업명 검색을 시작할 수 있어야 한다. 누락을 기록하고 임의 값을 채우지 않는다.

이 단계는 계약·예시 확정이며, API 검색과 실제 입력 검증 함수 구현은 이후 단계에서 진행한다.

`business_analysis`의 출력 구조 제안:

| 필드 | 내용 | 정보 부족 표현 |
|---|---|---|
| `commercialization_stage` | `demo`, `pilot`, `paid_operation`, `unknown` | `unknown` |
| `stage_reason` | 단계 판단 근거와 적용 제품·현장 | 확인되지 않은 사항 명시 |
| `customer_cases` | 고객명, 용도, 운영 상태, 유료 여부, 출처 ID | 빈 목록과 `information_gaps` 기록 |
| `deployment_costs` | 구매·구독·통합·유지보수 비용, 통화, 기간, 출처 ID | 수치 `null`, 미공개 표시 |
| `deployment_effects` | 효과 지표, 값·단위, 비교 기준, 측정 조건, 출처 ID | 수치 `null`, 정성 주장만 기록 |
| `regulatory_risks` | 해당 현장의 위험, 확인된 인증 상태, 확인 필요 사항, 출처 ID | 확인 불가 표시 |
| `evidence_assessment` | 주장별 근거 수준과 자료 간 모순 | 검증 불가 이유 명시 |
| `information_gaps` | 미확인 정보와 고객·기업에 추가로 물을 질문 | 확인하지 못한 항목 모두 기록 |
| `summary` | 현장 도입·사업성 핵심 결론 | 분석 한계 포함 |

각 사실 주장에 `source_ids`를 연결한다. 출력은 Pydantic 검증 후 `model_dump()`로 State의 `dict`에 저장하고, `references`에는 인용된 `Evidence` 객체만 추가한다.

### 4단계: 검색 전략

초기 제안은 주제별 1회씩 총 3회, 호출당 최대 5개 결과다. 실제 실행 결과에 따라 조정하며 변경 이유를 작업 기록에 남긴다.

| 주제 | 질의 예시 | 확인 대상 |
|---|---|---|
| 고객·상용화 | `{기업명} {제품명} customer deployment paid contract pilot` | 도입 고객, 실제 운영, 유료 여부 |
| 비용·효과 | `{기업명} {제품명} pricing maintenance productivity ROI case study` | 가격, 통합·유지보수 비용, 도입 효과 |
| 안전·규제 | `{기업명} {제품명} safety certification deployment` | 해당 제품·현장의 안전 인증과 도입 제약 |

기업 국가와 자료 언어에 맞춰 한국어·영어 질의를 선택한다. 기업 자료, 고객 측 발표, 관련 기관 자료를 우선하며 보도자료 재게시를 독립된 교차 검증 자료로 세지 않는다. 검색 요약만으로 판단한 경우 원문을 확인한 것처럼 표현하지 않는다.

### 5~6단계: 구현 흐름

1. 입력의 기업명과 필요한 분류 정보를 검증한다.
2. 검색 질의를 생성하고 허용된 `web_search`를 호출한다.
3. 기업·제품 관련 자료를 정리하고 출처 ID 중복을 제거한다.
4. 근거와 입력을 LLM에 전달해 구조화된 분석 결과를 받는다.
5. 출력 형식과 인용 ID를 검증한다. 제공하지 않은 ID가 나오면 검증 실패로 처리한다.
6. 실제 인용한 자료만 선별한다.
7. `business_analysis`, `references` 두 키만 반환한다.

State를 직접 변경하지 않는다. 누적 `references` 전체를 다시 반환하면 reducer가 중복 추가하므로 이번 Agent가 사용한 자료만 반환한다. 기업이 바뀌면 이전 기업의 분석을 읽어 재사용하지 않고 현재 기업 결과를 새로 작성한다.

검색 결과가 없는 상황과 API 장애를 구분한다. 정상 검색에서 관련 자료가 없으면 정보 부족 결과를 만들고, 인증 오류·호출 실패·출력 검증 실패는 빈 성공 결과로 숨기지 않는다. 재시도를 넣으면 횟수와 종료 조건을 명시한다.

## 4. 분석 판단 기준

### 상용화 단계

| 단계 | 필요한 근거 | 단정하면 안 되는 경우 |
|---|---|---|
| 시연 (`demo`) | 데모, 전시, 통제 환경의 작동 사례 | 시연 성공을 고객 현장 운영으로 확대 해석 |
| 시험 운영 (`pilot`) | 실제 고객 현장의 시험·PoC 운영 근거 | PoC, LOI, MOU, 파트너십을 유료 운영으로 간주 |
| 유료 운영 (`paid_operation`) | 고객 현장 운영과 유료 계약·대금 지급 근거 | 고객 로고나 수주 발표만으로 운영·유료 여부 확정 |
| 확인 불가 (`unknown`) | 분류에 필요한 근거가 없음 또는 서로 모순됨 | 자료 부재를 사업 실패로 판단 |

유료 여부와 실제 운영 상태는 별도로 확인한다. 유료 PoC는 시험 운영으로 기록하며 유료라는 사실을 함께 적는다. 단계는 출처가 뒷받침하는 제품·고객 사례에 한정하고 기업 전체의 보편적 운영 수준으로 일반화하지 않는다.

### 비용과 도입 효과

- 가격은 금액, 통화, 대상 제품, 계약 기간, 포함·제외 항목을 함께 기록한다.
- 도입 비용은 제품 가격 외에 통합, 설치, 교육, 유지보수 등이 공개되어 있는지 확인한다.
- 생산성·비용 절감 수치는 단위, 비교 대상, 기간, 측정 현장과 조건을 함께 기록한다.
- 기업 발표 수치와 고객 확인 수치를 구분한다. 다른 현장에도 같은 효과가 난다고 가정하지 않는다.
- 조건이 부족하면 ROI나 회수 기간을 임의 계산하지 않는다. 미공개 가격을 유사 제품 가격으로 대체하지 않는다.

### 안전·규제 위험

운영 국가, 사용 현장, 사람과의 접촉 여부, 제품 종류를 확인한 뒤 관련 위험을 기술한다. 특정 인증이나 법적 요건은 해당 관할의 공식 자료로 확인된 경우에만 필수 요건으로 표현한다. 자료에 인증 언급이 없다는 이유만으로 미인증·위법이라고 판단하지 않는다.

### 근거 수준

| 구분 | 판단 기준 | 기록 방식 |
|---|---|---|
| 교차 확인 | 고객·기관 등 다른 주체가 같은 구체적 사실을 확인 | 일치하는 사실과 각각의 출처 ID 기록 |
| 단일 출처 확인 | 원 출처 1개에서 구체적 사실 확인 | 발표 주체와 독립 검증 여부 기록 |
| 주장 수준 | 홍보 문구 또는 측정 조건 없는 효과 주장 | 검증되지 않은 주장으로 표시 |
| 확인 불가·모순 | 자료 부족 또는 출처 간 상충 | 부족한 정보·상충 내용·추가 확인 질문 기록 |

근거 수준은 사실 주장별로 평가한다. 출처 수만으로 신뢰도를 높이지 않으며 자료 발행일과 운영 사례의 시점을 구분한다.

### 투자 판단 Agent와의 경계

이 Agent는 도입·실적·비용·위험 근거를 전달한다. 투자 판단 Agent가 전체 분석을 종합해 점수와 `invest`, `conditional`, `hold`를 결정한다. 위험·핵심 정보 부족은 명시적으로 전달하되 4번 Agent가 투자 상태를 직접 수정하지 않는다.

| 검증 사례 | 기대 결과 |
